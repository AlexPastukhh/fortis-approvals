## Reduced scope (owner deferred external history)

This MVP intentionally does **not** include the separate independent immutable/monotonic journal. Backups or old binaries can revert a restriction. The only local audit is an ordinary same-DB event table, not independently verifiable anti-rollback. Before owner production rollout, a separate release decision must explicitly accept this limitation and prove all active ingress, workers, owner inventory and restore paths use the same guarded Core; ordinary `Core` still bypasses the opt-in local DENY overlay (proven by existing negative test).

`OwnerLocalDenyApply` in `extensions/owner_policy_local_deny_apply_phase6c1.py` requires an explicitly created `LocalDenyCore`, a real `OwnerWebAuthn` bound as `core.owner_verifier`, and trusted **injected** installed-source and credential-generation digests. The inputs are **not** proof of live host attestation: no trusted runtime identity reader is installed by this PR. The caller is a future **owner-only** HTTP bridge and MUST independently validate secure Host/Origin, session cookie and CSRF before ever constructing or forwarding input. This source class itself has no HTTP route.

Only an existing, literal **exact** `(actor,service,operation,target)` Core policy with configured `ASK` or `ALLOW`, existing loaded adapter and active actor grant may be narrowed to `DENY`. Callable/global/actor-wide/unknown policies, missing grant, prior local DENY, stale configured values, wrong versions and wildcards are refused. **There is no way to grant `ALLOW`, restore `ASK`, remove a denial, change PowerShell command-policy enforcement, or bypass machine approval via this adapter.**

## Owner ceremony and atomicity

1. `begin_deny` requires authenticated owner session+CSRF and an exact, closed candidate schema (actor/provider/operation/target, old literal policy, expected `LocalDenyCore.policy_version`, expected global revision, reason code). Under the Core DB lock it validates that the active config and local restrictions still match. It creates a new purpose `OWNER_LOCAL_EXACT_DENY_APPLY_V1`, fresh UUID, 90-second expiry, and pinned source/credential digests. The `OwnerWebAuthn._begin_assertion` challenge is separately bound to session hash, descriptor digest and expiry, with REQUIRED user verification. **Phase 4/5 draft-review proof is never reused.**
2. `finish_deny` requires the same owner session+CSRF and consumes that purpose-specific ceremony **once**, including on tampered descriptors or wrong UV/origin. It checks exact binding and calls real `OwnerWebAuthn._finish_assertion`, which verifies RP/origin, signature, active credential, UV and counter. After that, `BEGIN IMMEDIATE` on the **same Core SQLite file** rechecks the actor/grant/exact old policy, revision and READY gate; in one transaction it inserts an exact DENY, CAS-advances revision and writes `owner_local_policy_events` with original change UUID/owner/old and new revision. Failed CAS rolls back the local change. No adapter side effect is invoked.
3. After commit, same-DB readback verifies the event and DENY; `readback` provides owner-session-only lost-response lookup by original UUID. Never blindly retry a consumed challenge. Core already fingerprints policy version into PENDING approvals and rechecks it before dispatch under the same DB write lock. Already DISPATCHED/UNCERTAIN outcomes remain untouched; this is **not** remote effect rollback.

The new `owner_local_policy_events` table belongs to the same opt-in SQLite schema. Prior source-only two-table test databases are **not automatically migrated**; an incomplete local schema stops startup instead. There is no independent receipt signature, remote ledger or owner emergency database repair.

## Objective, split ownership and critical semantics

The planned **outer owner-managed method policy** is `DENY / ASK / ALLOW` for a *precise* provider + operation/method + actor + target/environment; the owner should eventually see inventory, effective rule, preview/diff, prerequisites and apply controls in **Owner Dashboard → API и политики**. This is **planned**, not the current live policy editor. Existing trusted Core policy and per-actor grants still control execution. `DENY` stops; `ASK` creates a Core `PENDING` request and requires owner WebAuthn for **that method invocation**; `ALLOW` is unattended **only inside its exact approved method scope**. Unknown/unconfigured operations fail closed. A method's broad HTTP verb, discovery or read-only-looking name never implies `ALLOW`.

For Windows `powershell.execute` there is a separate **inner command-specific Dynamic ASK evaluator** owned by `fortis-powershell-executor`, not by a second Gateway Dashboard policy editor. External method `DENY` always denies; external method `ASK` requires owner approval regardless of inner ALLOW; external `ALLOW` still goes through Windows command evaluation. Internal `DENY` vetoes even an approved outer ASK; internal `ASK` needs Core owner approval; internal `ALLOW` may execute only with external ALLOW **and Windows enforcement/proof**. The agreed aggregate precedence is `DENY > ASK > ALLOW`. If both layers ask, there should be **one** Core `PENDING`/WebAuthn decision, not nested approvals. This combined policy and V2 proof **do not exist in the active V1 machine route**. Never switch a general PowerShell shell to ALLOW by a policy-map change. The Windows Executor has its own [Dynamic ASK implementation backlog](https://github.com/AlexPastukhh/fortis-powershell-executor/blob/main/docs/BACKLOG-IMPROVEMENTS.md#executor-dynamic-ask); Script Center is setup/launcher integration, not the policy authority.

Owner WebAuthn **approval of an ASK action** is distinct from owner WebAuthn **authorization to change an access rule**. The latter must be a fresh strong UV-required proof bound to that exact change, checked again at the atomic commit; a login session, previous action approval, draft review, preview hash or reusable token cannot substitute for it. The AI/machine client may discover *its* capabilities, submit typed action ASK and (as a future design) suggest a policy proposal, but **cannot grant itself permissions, change policy/credentials/grants, or impersonate the owner**. No owner-only HTTP routes through the machine API.

## Runtime and implementation boundaries

- `fortis_approvals/core.py`: current source for strict request states, policy lookups, default DENY, action `ALLOW/ASK`, owner decision and execution-time recheck. It has **no persisted, owner-editable active policy store**. Distinguish effective config/actor grants from stored draft state.
- `fortis_approvals/incidents.py`: owner-only HTTP routing for inventory, preview, review; its presence in Git does not mean installed Gateway serves it. `fortis_approvals/static/index.html` and `static/app.js` hold the read-only inventory/preview and opt-in review UI.
